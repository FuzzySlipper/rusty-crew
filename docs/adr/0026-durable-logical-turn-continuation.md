# ADR 0026: Durable Logical Turn Continuation

Status: Accepted design for task 6364

Date: 2026-07-28

Related tasks: `#6362`, `#6363`, `#6365` through `#6373`

Supersedes: ADR 0023 where its buffered-turn state machine makes elapsed
timeouts or finite buffer/round ceilings terminal for an otherwise healthy
logical turn.

## Context

Rusty Crew's production Chat Completions and OpenAI Responses loops are
Rust-owned and share the buffered brain runtime. Their current execution model
still equates one scheduler wake, one in-process provider/tool loop, and one
logical user turn.

That equivalence creates hard stops:

- a wake timeout can fail healthy work based only on elapsed wall time;
- finite Chat Completions and Responses round counters fail productive loops;
- buffer pressure can turn retention policy into a failed turn;
- repeated-call checks do not distinguish state-changing work from a loop;
- active provider/tool loop state is lost on service restart;
- delegated `maxDurationMs` expires from session creation even while work is
  progressing.

The code-backed baseline is
`docs/active-turn-termination-guard-inventory.md`.

Long-lived agent turns are normal. A finite execution quantum is useful for
fairness, persistence, deployment, and crash recovery, but it is not a valid
logical-turn lifetime. Rusty Crew needs to yield one execution epoch and resume
the same logical turn without fabricating completion, failure, a new user
message, or duplicate side effects.

## Decision

Rust owns a durable **logical brain turn** above provider-specific execution
epochs.

```text
logical turn (stable identity and frozen admission facts)
  -> continuation checkpoint 0
    -> execution epoch 0
      -> provider and host-tool operations
      -> durable progress + projection outbox
      -> completed | yielded | attention_required | cancelled
  -> continuation checkpoint 1
    -> execution epoch 1
      -> ...
```

A logical turn has no finite healthy-work lifetime. Execution epochs use a
bounded quantum checked only at safe operation boundaries. Reaching a quantum
persists a checkpoint and makes the same logical turn runnable again. It never
emits `WakeFailed`, a failed assistant message, or a new user turn.

TypeScript remains the concrete tool/adapter executor and browser/service
projection boundary. It does not decide whether a logical turn yields,
continues, pauses, completes, or fails.

## Identity Model

The identities are deliberately separate:

| Identity | Lifetime | Purpose |
| --- | --- | --- |
| `LogicalTurnId` | one admitted user/message/scheduled activation through terminal outcome | stable owner of context, progress, cancellation, and chat projection |
| `WakeId` | one Rust scheduler activation ticket | identifies the frozen body activation that created or resumed work |
| `ContinuationId` | one immutable checkpoint | identifies the exact state from which an execution epoch may start |
| `ExecutionEpochId` | one claimed process execution | fences stale workers and restart/retry races |
| `OperationId` | one provider request or host-tool effect | provides idempotency, reconciliation, and projection provenance |
| `ProjectionId` | one logical chat/activity mutation | makes replay and SSE delivery idempotent |

The initial wake creates the logical turn and checkpoint zero. A continuation
wake references the same `LogicalTurnId`, a new `WakeId`, and the checkpoint it
claims. Existing wake IDs remain useful correlation facts; they are not used as
the durable logical-turn identity.

IDs are generated by Rust. TypeScript receives them and returns them
unchanged. No identity is inferred from array position, process-local counters,
provider chunking, or current session state.

## Lifecycle

```text
admitted
  -> runnable
  -> running
  -> yielded -> runnable -> running ...
  -> attention_required -> runnable
  -> cancel_requested -> cancelled
  -> completed
  -> failed
```

`completed`, `cancelled`, and `failed` are terminal. `yielded` and
`attention_required` are explicitly nonterminal.

`failed` is reserved for a terminal provider rejection or a proven
unrecoverable contract/integrity failure. Transient transport failure,
operation timeout, no-progress detection, unknown external-effect outcome,
missing credentials after restart, or incompatible hot-swap state produces
`attention_required` or a retryable yield instead.

There is no `timed_out` logical-turn phase. Time may bound one operation, a
renewable claim, a message's relevance, or a scheduler quantum target. Time
alone cannot fail a healthy logical turn.

The following shapes are normative in meaning. Task 6365 may split them across
`core-protocol`, `brain-runtime`, `core-engine`, persistence repositories, and
generated bridge artifacts.

Secrets are never stored in the binding snapshot or checkpoint. Credential ID,
revision, and fingerprint pin selection; the host resolves the secret at the
moment of a provider operation.

### Frozen Admission Input

Checkpoint zero durably captures the data now hidden behind ephemeral runtime
buffers:

- frozen `BodyState` or an immutable body snapshot reference and hash;
- system prompt and role assembly, or immutable content-addressed references;
- selected model/tool schemas and their revisions;
- durable input attachment references;
- initial provider-state input and absence reason;
- the transcript/event cursor from which projection began.

Mid-turn messages remain body-owned next-turn deltas under ADR 0003. A
continuation does not silently incorporate newly arrived body state. Explicit
steering policy may create a new frozen input amendment with its own durable
sequence; it may not mutate an earlier checkpoint in place.

### Checkpoint

```rust

    module_id: String,

    module_state: BrainContinuationState,
    operation_cursor: u64,

}

enum BrainContinuationState {
    ChatCompletions(ChatCompletionsContinuationState),
    OpenAiResponses(OpenAiResponsesContinuationState),
}
```

The common envelope is typed Rust authority. Module state is a versioned,
tagged Rust enum, not arbitrary TypeScript JSON. Serialization may use a
versioned JSON payload in storage, but only the owning Rust module decodes,
validates, migrates, or replaces it. Unsupported versions request operator
attention; they do not fall back to an old loop.

Chat Completions state includes committed neutral/provider messages, reasoning
history policy, completed tool exchanges, provider request sequence, current
provisional assistant operation, token usage, and no-progress evidence.

Responses state includes committed input/output items, encrypted reasoning
items where required, `previous_response_id`, response-chain policy, completed
function-call outputs, provider request sequence, usage, and no-progress
evidence.

## Epoch Claims And Scheduler Fairness

Only one execution epoch may own a logical turn at a time. Rust acquires a
compare-and-swap claim containing:

- `logical_turn_id` and expected turn revision;
- source `continuation_id` and sequence;
- `execution_epoch_id`;
- service instance/worker identity;
- renewable claim generation and expiry.

Claim expiry is crash-recovery authority, not logical-turn failure. A stale
epoch cannot commit an operation, checkpoint, projection, or terminal outcome
after another generation owns the turn.

The execution quantum is a fairness target evaluated only after a safe
provider or tool operation boundary. It may be expressed as completed
operations, retained semantic events, or elapsed scheduler occupancy. It has
no terminal maximum. If the target is reached:

1. commit all completed operations and projections;
2. append the next immutable checkpoint;
3. transition `running -> yielded -> runnable` atomically;
4. enqueue one continuation ticket;
5. release the claim;
6. let the scheduler choose another runnable session before reacquisition.

The scheduler keeps at most one runnable ticket per logical turn and uses
session/profile fairness rather than a tight self-resume loop. It may apply
priority, weighted round-robin, and per-profile concurrency, but it may not
discard or fail work because it has yielded many times.

An in-flight HTTP request or tool subprocess is not killed merely because the
quantum target elapsed. The boundary is checked after that operation returns,
is explicitly cancelled, or reaches its own operation-level timeout.

## Provider And Tool Operations

Every side-effecting or restart-sensitive operation is durably planned before
dispatch:

```rust
enum TurnOperationKind {
    ProviderRequest,
    HostToolExecution,
}

enum TurnOperationPhase {
    Planned,
    Leased,
    Completed,
    OutcomeUnknown,
    Superseded,
}

struct LogicalTurnOperation {
    operation_id: BrainOperationId,
    logical_turn_id: LogicalTurnId,
    continuation_id: ContinuationId,
    execution_epoch_id: ExecutionEpochId,
    kind: TurnOperationKind,
    request_fingerprint: String,
    idempotency_key: String,
    phase: TurnOperationPhase,
    result_ref: Option<String>,
    revision: u64,
}
```

### Tool Effects

The neutral host request gains `logical_turn_id`, `operation_id`, and an
idempotency key. Before execution Rust commits `Planned`, then leases it to the
host. A completed tool result is committed before the provider loop can consume
it.

On replay:

- an identical completed operation reuses its stored result;
- a conflicting operation fingerprint is rejected;
- an unleased planned operation may be executed;
- an expired lease with a tool-provided idempotent receipt may reconcile or
  retry;
- an expired lease for a non-idempotent tool has `OutcomeUnknown` and pauses
  for operator attention.

Rusty Crew does not promise impossible exactly-once execution across an
arbitrary external side effect. It promises exactly-once result consumption,
idempotent replay where a receipt supports it, and visible attention instead
of blind duplicate execution where the outcome is unknowable.

### Provider Operations

Provider generation is not itself an external world side effect, but its
stream may already be visible to the user when a process dies. Each request is
one durable operation with provisional output segments.

At a safe provider terminal boundary, the operation commits its canonical
assistant/output items, response identity, usage, and next module state. If the
service dies mid-stream:

- the partial operation becomes `OutcomeUnknown`;
- already completed tool effects remain committed and are not rerun;
- the brain retries or reconciles from the last committed module checkpoint;
- provisional output from the abandoned operation is marked superseded;
- the replacement operation receives a new `OperationId` but remains in the
  same logical turn.

Responses may reconcile by stable response/item IDs when available. Chat
Completions retries from committed messages because it has no server-side
response chain. Provider-specific recovery lives in the Rust brain crate, not
in TypeScript service glue.

## Projection And Duplicate Prevention

Streaming remains user-visible, so restart safety cannot rely on hiding all
output until terminal completion.

Rust persists a projection outbox with stable `ProjectionId`s before
TypeScript/browser/observation delivery. Projection records identify the
logical turn, operation, semantic channel, and monotonic cursor.

Assistant text/reasoning segments have lifecycle:

```text
provisional -> committed
provisional -> superseded
```

Only committed provider messages and tool results enter future model context.

### Tool-requested turn disposition

Tool execution has two intentional stop semantics that must remain distinct at
the brain-host boundary:

- `complete_turn` means the tool has produced the terminal action for the
  current logical turn, such as `deliver_completion_md`.
- `suspend_external` means an external waiter has been registered and a later
  external event will request the next wake, such as a pending GitHub check
  gate.

These are typed dispositions, not a generic terminate boolean. The disposition
travels with the committed host-tool result into the Rust provider loop. The
loop emits the ordinary tool-result event, records the result in provider
state, and then emits its successful terminal action without issuing another
provider request. It does not simulate completion by cancelling the native
run. Explicit operator cancellation and unexpected native terminal failures
retain their normal cancellation or failure semantics.

For `suspend_external`, registration of the external waiter happens before the
host-tool result is submitted. The current wake then completes cleanly, while
the waiter owns admission of the later wake when the external event becomes
terminal.
Provisional segments may appear in Rusty View, but retry/restart emits a typed
supersession event so the canonical chat read model replaces or withdraws them
instead of appending duplicate text.

The following writes use stable idempotency keys:

- tool call start/result;
- assistant text/reasoning segment;
- provider status and usage;
- assistant action batch;
- assistant terminal message;
- lifecycle progress/yield/attention event;
- Den Observation or other adapter projection receipt.

SSE replay reuses stored event IDs and cursors. TypeScript adapter failure is
degraded observability and retries the outbox; it cannot change turn state.

## Progress And No-Progress

Rust tracks two independent concepts:

- **liveness**: provider bytes, heartbeats, tool process activity, lease
  renewal, or stream transitions show that execution is alive;
- **semantic progress**: durable state relevant to completing the task changed.

`LogicalTurnProgress` records stable digests/cursors for:

- committed provider message/output items;
- committed tool effect and result fingerprints;
- accepted BrainAction or body/session revision;
- assistant content length/hash;
- delegated completion and fan-out progress;
- module checkpoint state.

Repeated calls are not automatically a loop. The same tool and arguments may
be productive when the result fingerprint or relevant state revision changes.
A no-progress sample requires the same operation intent, equivalent result,
unchanged relevant state digest, no new committed assistant content/action,
and no completion progress.

Policy is staged:

1. first confirmed no-progress repetition returns model-visible correction
   guidance;
2. later consecutive no-progress samples may yield to scheduler fairness;
3. the configured threshold transitions to `attention_required` with the
   evidence chain and suggested operator actions;
4. no-progress never fabricates `completed` or `failed`.

Elapsed time, token usage, or provider reasoning text alone is not semantic
progress. They remain liveness/diagnostic signals.

## Operator Attention

Attention is a durable nonterminal state. Reasons include:

- non-idempotent tool outcome unknown after crash;
- repeated confirmed no-progress;
- provider credentials unavailable after restart;
- incompatible checkpoint/module version;
- provider protocol/configuration failure requiring a change;
- requested profile/provider hot swap cannot preserve state automatically;
- storage or invariant repair required before safe continuation.

Rust emits a typed lifecycle event with reason code, summary, evidence/debug
references, available resolution actions, current revision, and whether a
retry with unchanged inputs is safe. Chat and activity APIs project the event,
but it is excluded from model context unless an operator resolution explicitly
adds guidance.

Resume/resolve APIs use expected revision and a named resolution action. A
generic blind `resume` is rejected when the state requires discard, rebind, or
manual effect confirmation.

## Cancellation Races

Cancellation is a compare-and-swap mutation on the logical turn. It increments
`cancellation_generation`, changes the phase to `cancel_requested`, revokes any
runnable continuation, and invalidates older epoch claims.

Every epoch checks the generation:

- before dispatching a provider/tool operation;
- after the operation returns;
- before committing provider state or a checkpoint;
- before publishing terminal actions/projections.

Race outcomes are explicit:

- completion committed first: cancel returns `already_terminal`;
- cancellation committed first: stale completion/checkpoint commits fail;
- a tool completed externally after cancellation: retain its receipt and mark
  `completed_after_cancel`, but do not feed it into a cancelled turn;
- provider output arriving after cancellation may be retained only as bounded
  diagnostics and is not projected as canonical assistant output;
- repeated cancellation with the same key is idempotent.

Cancellation never deletes checkpoint, operation, or effect evidence needed to
explain what happened.

## Restart Hydration

On startup Rust:

1. loads nonterminal logical turns and their current checkpoint;
2. expires stale execution claims without changing logical-turn phase;
3. reconciles leased provider/tool operations;
4. moves safe work to `runnable` and unsafe unknown effects to
   `attention_required`;
5. restores at most one continuation ticket per runnable turn;
6. replays pending projection outbox records;
7. resumes through the ordinary scheduler path.

A turn that was durably `yielded` resumes directly. A turn that was `running`
is first reconciled; process death is not represented as user cancellation or
assistant failure.

SQLite and PostgreSQL implement identical transactional semantics. Backend
parity is part of task 6365 acceptance, not a later migration concern.

## Profile And Provider Changes

The binding snapshot is frozen for a logical turn. Ordinary profile/provider,
prompt, tool-profile, credential, model, temperature, effort, or reasoning
configuration changes apply to the next logical turn and never silently alter
an active one.

An explicit active-turn rebind is allowed only at a safe checkpoint:

1. record a rebind request with expected logical-turn revision;
2. let the current operation finish, or explicitly cancel it;
3. ask the Rust brain module for a typed compatibility plan;
4. preserve neutral committed transcript/tool state;
5. retain compatible provider state or invalidate it with a visible reason;
6. create a new binding generation and continuation checkpoint;
7. resume the same `LogicalTurnId`.

Responses `previous_response_id` state generally cannot cross provider/model
identity and falls back to a Rust-owned replay plan when supported. If the
module cannot safely translate state, the turn enters `attention_required`
instead of using a legacy fallback or silently starting over.

## Lifecycle Events And Diagnostics

Logical-turn lifecycle events are a Rust protocol family separate from
`BrainEvent`. The brain reports provider/content/tool facts; Rust coordination
reports lifecycle authority.

Initial event kinds:

- `logical_turn_admitted`
- `continuation_claimed`
- `continuation_progress`
- `continuation_checkpointed`
- `continuation_yielded`
- `continuation_resumed`
- `logical_turn_attention_required`
- `logical_turn_rebind_requested`
- `logical_turn_rebound`
- `logical_turn_cancel_requested`
- `logical_turn_completed`
- `logical_turn_cancelled`
- `logical_turn_failed`

Diagnostics expose stable IDs, phase, binding generation, checkpoint sequence,
current/last epoch, claim age, last liveness and semantic-progress timestamps,
operation counts by phase, no-progress samples, attention reason, and restart
count. They do not expose prompts, credentials, raw tool output, or provider
secrets.

Lifecycle events are visible in Rusty View's debug/activity stream and may be
rendered in chat as unobtrusive system status. They are not included in the
model context window by default.

## Storage Ownership

Crew storage gains typed logical-turn repositories rather than another
`simple_kv` snapshot:

- `logical_brain_turns`
- `logical_brain_turn_checkpoints`
- `logical_brain_turn_operations`
- `logical_brain_turn_projection_outbox`
- optional content-addressed checkpoint blobs for large immutable payloads

Common lifecycle/revision/claim fields are queryable columns. Versioned module
state may be a typed serialized payload with a fingerprint and explicit
payload version. Large prompt/body/provider blobs are referenced by stable
content hash and governed retention; they are not copied into every
checkpoint.

Terminal retention is explicit and independent from active-turn correctness.
Active checkpoints and unresolved operation evidence cannot expire.

## Bridge And Code Generation

The canonical DTOs live in Rust and join the generated protocol family under
ADR 0024. TypeScript consumes generated types for lifecycle events,
checkpoints exposed to diagnostics, tool operation requests/results, and
continuation receipts.

The native bridge surface remains narrow and operation-oriented. It may expose
start/claim, drain, submit host result, cancel, and diagnostics calls, but it
does not accept TypeScript-authored lifecycle phase changes or arbitrary
checkpoint JSON.

No compatibility aliases preserve terminal continuation-limit reason codes.
Task 6372 deleted their code, config variables, diagnostics fields, tests, and
operator-facing docs after implementation and certification completed.

## Rejected Alternatives

### Set Very Large Or Disabled Loop Limits

This only hides the failure until a longer task appears and offers no restart,
fairness, or effect-deduplication semantics.

### Start A New User Turn On Every Yield

This pollutes transcripts and model context, changes command/message semantics,
and makes one task appear as many assistant turns.

### Keep The Provider Loop Alive Forever In One Process

This prevents fair scheduling, upgrades, and crash recovery and leaves active
state invisible to storage authority.

### Let TypeScript Serialize And Resume Arbitrary Brain State

This would move lifecycle authority back into the service host and make
provider-specific TS glue the future extension point. Rust modules own their
typed continuation state.

### Blindly Retry Every Tool After Restart

External side effects are not generally exactly-once. Unknown non-idempotent
outcomes require operator attention, not hopeful duplication.

### Treat Silence As Failure

Provider/tool silence may be slow healthy work. It can produce an operator
alert or operation-level timeout when configured, but it does not prove that
the logical turn should fail.

## Consequences

- Long turns can survive finite scheduler quanta and service restarts without
  becoming multiple chat turns.
- SQLite and PostgreSQL both carry more active state and write volume; typed
  repositories and bounded content-addressed blobs keep this reviewable.
- Streaming projections gain provisional/committed/superseded semantics.
- Tool execution gains durable operation identity and honest unknown-outcome
  handling.
- Active profile/provider changes become explicit and deterministic.
- The implementation is larger than raising constants, but it removes a class
  of recurring failures instead of moving their thresholds.
